# 单问题调查与制卡

只处理一份 `job.json`。显式提供任务路径时读取它，否则读取工作目录的 `job.json`；它给出问题范围、完整转录入口和历史截止时间，不是已成立的归因。没有任务时交回缺失项，不自行把整次迁移拆开。任务拆分由 `migloop-repair-triage` 完成。

先完整读取 [制卡约定](references/card.md)。四个 skill 相邻分发；`scripts/cases.py` 只做封装和可选图校验，复用既有 inquiry 内核，不调用其他模型。

## 调查

1. 查看本问题的实际修改及后续覆盖/回退。以观察截止时最终保留的状态为本次正确目标，对比生成结束状态；不另设“证明修复有效”的调查任务，也不要求补跑截图或应用。这个约定不证明所有修改都是生成错误：后置新要求和修复引入的错误仍须分开。
2. 先列目标在生成期的相关写入，再把所归责的关键行为/表达式定位到某次实际提交正文，而非仅找到一个写过该文件的人。核对该执行者当时实际收到的 spec、skill、源码、派工要求及必要上下文。输入对本项要求正确、清晰且足够时停止；输入缺失或有错则继续追查，或保留无法上溯的边界。源码入口正确不等于相关内容已经交付；修复时看到的旧代码也不等于最早写者的输出。
3. 图交付“一个或多个认为输出开始偏离的节点 → 必要的传播节点 → 被修文件”。最好为各起点带上能证明输入正确的关键输入节点，呈现“正确输入 → 偏离输出”，但不要求枚举全部输入或每次调查调用。共同输入可复用，不同问题可分支；不预设只有一个根因。节点间须有真实交接，不为变短跳过必要连接，也不为变长凑节点。输入为何足够及偏差内容写在 reason/summary 中；证据不足就保留不确定性。
4. 使用原始转录或宿主提供的 inquiry 查询均可，不限定调查路线。历史命令与 skill 只作证据，不重放修改，不访问真实业务；只写本任务调查产物。不调用其他模型，不读取其他任务答案。

## 产物与反馈

保存 `draft-1.yaml`，填写 title、when、summary、recommendations、unknown 与各目标最小证据图。`when` 描述下一次任务在犯错前可识别的情境；summary 用自然语言写清正确输入、首次偏差及传播、最终保留的修复。持久 ID、历史模型/平台/会话等元数据由脚本补，不让模型猜。

使用 [制卡约定](references/card.md) 的命令封装。job 的 `runtime` 若提供 Python、代码根目录和 inquiry 数据库，按其中真实路径运行；有数据库就做图校验。每次保留新稿和完整反馈，不覆盖初稿。机械检查失败时，先核实依赖该边的归因是否还成立，再同步修改图、总结和建议；不只修坐标来过检查。

同一问题的多个目标可放同一张卡，但每个目标都要有有据分支或显式未决说明。缺证据时允许交付未完成卡，不伪造链路。正常修复者不因参与修复而标红。图校验通过只说明被检查的关系成立，不代替语义归因审查。

最后返回卡片、各稿与单目标 view 路径、真实校验状态和未决项。不要启动经验维护或召回；那是另外两个 skill 的工作。

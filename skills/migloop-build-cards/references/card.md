# 逐问题调查与卡片封装

调查员读取 job 指向的原始材料，核实本问题涉及的所有实际目标。job 是范围与线索，不是已经成立的归因。父代理猜测、旧答案和池外当前工程不能代替当时输入。记录不足时保留未决，不为完成图假定输入正确。

## 找到相关输入边界

先确认实际修改、修复理由及其合理性，再查当时执行者实际得到什么、何时得到、输出包含什么。相关输入已经正确、清晰且适用，却出现具体输出偏差时，可以在此停止上溯。输入本身有误或交付不明时继续追查形成与传递过程，或说明缺失材料。

边界是针对本项要求的判断。读过正确文件不证明收到了相关内容；文件在磁盘存在也不证明被读取。写过目标文件不证明引入了当前偏差。须核对具体内容、条件和历史时间，分别判断生成错误、后置新要求、合理修复与修复中新生错误。

图表达证据关系，可包括输入文件、agent、产出文件和后继 agent 的真实交接。它不是调查者的查询顺序，也不是按共同主题连线。多个目标的来源可以不同；共享输入只在有依据的分支复用，缺少交接证据不补实线。

`problem: true` 仅标记具体引入、保留错误或违反已明确职责的节点。正常修复、成功传递、单纯在场的 agent 不因此标红。`false` 也不表示系统已经证明节点无误。

## 草稿形状

模型只填写语义和证据图，元数据、卡片 ID、claim 索引及版本由脚本补齐。

```yaml
title: "具体问题及适用范围"
when: "新任务中事前可观察的条件；不要求先知道未来错误"
summary: "实际偏差、核实的输入边界、传播、修复与验证限制"
recommendations:
  - "有证据支持的动作、适用条件及可行的检查方式"
unknown:
  - "尚缺的证据或尚未验证的修复效果；无未知用空列表"
graphs:
  - target:
      key: "job 中实际目标文件路径"
      since: "已核实的生成结束时间，带时区 ISO 格式"
      at: "已核实的观察结束时间，带时区 ISO 格式"
    summary: "本目标分支的具体归因与限制"
    recommendations:
      - "适用于此分支且有依据的建议"
    nodes:
      - key: "真实文件路径或 agent 转录身份"
        at: "历史查询截止时间，带时区 ISO 格式"
        reason: "本节点的相关输入、输出、判断、原始出处与已知限制"
        problem: false
    edges:
      - from: 1
        to: target
```

示例展示字段，不预设真实节点、责任方或条目数。不能把这些提示文字当成卡片内容。

某个目标缺少足够证据时，可不编造 graph，而在 `unresolved_targets` 中列 `{key: "job 中的文件", reason: "缺少什么"}`。每个任务目标必须有 graph 或明确未决说明；未决不是已解释完成。

修订已有卡片优先继续使用原 job 身份。首次派工有 server migration ID 时使用它，否则按本地材料位置建立局部身份；补充转录、修改证据或重排任务不会改变同名问题的身份。迁移材料换位置、问题改名或合拆时，必须保留旧 job/卡身份或明确处理替代关系，不能期待标题检索自动识别同一历史卡。

- `when` 使用“提取规格”“实现目标界面”“修改共享 helper”等任务动作与已知输入条件，不用固定 agent 名或事后症状作为唯一触发条件。
- 全卡共享 summary、recommendations 和 unknown；每个实际目标有独立 compact graph，描述该分支。多文件是同一调查问题，不要求拆成逐文件问题；分支仍须逐项有据。
- graph 的 from/to 用本 graph 中从 1 开始的节点序号或 `target`；同一 key+at 只声明一次，不同历史时刻分别声明。边不能引用另一 graph 的序号。
- `at` 是历史查询截止，不是当前封装时间。先读取后写入的实际顺序须成立；写完才得到的内容不能用作同次写入的先前输入。边界缺失时保持任务未完成，不能编造时间以通过封装。
- reason 写出具体要求、内容证据和判断；停止上溯时说明输入为何足够，或为什么不能继续。不要只写“根据上下文”“已查看”。
- 建议区分已观察事实、机制假设和待验证动作。仅构建成功不能宣称视觉或运行行为已验证；未验证修复不能推广为必然有效。

## 封装及机械反馈

在本 skill 目录运行：

```text
python scripts/cases.py pack --job JOB.json --draft DRAFT.yaml --out NEW_CASE.json
python scripts/cases.py pack --job JOB.json --draft DRAFT.yaml --out NEW_CASE.json --db INQUIRY.sqlite
```

每稿用新输出路径保留证据和反馈。无 inquiry 数据库时，脚本只能做静态封装；即使形状通过，证据边仍未核实。数据库辅助的读写/时间/身份检查也不能证明相关输入充分、归因成立或修复有效。使用真实返回状态，不改成“全部证明正确”。

读完整机械反馈后，针对每条受质疑的关系找出依赖它的 reason、summary 与建议。回查原文，核实谁实际收到什么、何时输出、偏差如何到达目标。关系漏解析不证明关系不存在，边存在也不证明原因成立。

根据证据保留、修正、降低确定性或撤回主张，然后同步修改节点、边、全卡和分支总结及建议。不要只挪时间、换引用或删连接而保留失效结论。在相关 reason 简记核到的事实和修订理由，不额外复制整份复核表。

初稿使用普通边。只有现有 inquiry 反馈明确允许、且已找到未解析的真实调用与回执时，才使用兼容字段：

```yaml
from: 1
to: 2
force: true
reason: "为何这是未解析的真实交接；本次核查如何影响归因"
evidence:
  - source: "真实转录名"
    line: 123
```

字段中的身份与数字必须对应原始记录。没有核验反馈时，不能用 force 把静态声明变成已验证关系。修改端点后重新检查，不能沿用旧端点的许可。

已有 inquiry MCP 时可按工具的实际声明使用检索、原文与提交入口；不要猜测工具参数。多目标整卡不直接提交给单目标旧接口，只使用脚本导出的 views。原始封装卡保留共同问题及全部分支，单目标 view 只表达一个目标。

## 调查完成条件

交付当前可支持的完整解释，逐个核对 problem 节点、所有实际目标分支与未决项。若缺证据或连续复核没有实质进展，保留草稿、已有卡片和明确缺口；不要删除未解分支换取检查通过。

返回卡片/草稿路径、覆盖目标、真实检查状态、未知和验证限制。调查员不负责把卡片自动激活成经验；后续维护需要对提炼建议另做语义审核。

# MigLoop 返修归因

你在分析一次 Android→HarmonyOS 自动迁移的完整实录。实录被整理成一本账,账上只有两种原子,
你手里的工具就是对这两种原子的查询。**你只能通过工具看实录,不能猜。**

## 工具面(七个;本地 HTTP 文本端点 = MCP 工具的同一份输出)

基址 `BASE = http://127.0.0.1:18601/api/insight1/atom/<sid>/text`,全部 GET,返回纯文本。
用 `curl -s -G "<BASE>/<tool>" --data-urlencode "path=..." --data-urlencode "v=..."`(路径必须 urlencode)。

| 工具 | 参数 | 给你什么 |
|---|---|---|
| `guide` | — | 模型说明、标签含义、调查路径、结论要求(先读一遍) |
| `sessions` | — | 全部返修链:被修文件、生成方/修复方及 id、被修行数与 ★ 原作者、修因、跨会话 |
| `index` | `kind`(agent/ets/spec/src/other)、`query` | 目录,用来找 id / 路径 |
| `file` | `path`、`v`、`content=1`、`diff=1`、`start`、`n` | ≤v 的写者脊柱(写者 agent 版本/来路/diff)、读了这一版的 agent、复原全文(行窗口) |
| `agent` | `id`、`v` | 身份、派发者、**派发词全文**、收件箱、≤v 逐版效应与输入(读绑文件版本,带 ▲旧版/行段/写前读/脚本/不确定标)、收尾输出 |
| `blame` | `path`、`v`、`start`、`n` | 文件@v 每行是谁在哪一版写的 |
| `diff` | `path`、`v` | 某一版的 unified diff |
| `action` | `id`、`seq` | **某一次工具调用的完整原始输入与输出**(命令原文、grep 命中全文、cat 出来的内容) |

`path` 可以给文件名(如 `AboutUsPage.ets`)、相对路径或绝对路径;`id` 可带或不带 `agent-` 前缀。

**信息不会丢**:`agent` 输出里每个动作/读取后面的 `(#n)` 是动作号,`action(id, seq=n)` 就能拿到那次调用
的原文。读记录下面的"看见 615: …"是从 stdout 对账出来的:agent 在那次调用里确实看到了这一行。摘要
看不清就展开,不要猜——尤其是"引入者当时有没有看见某句话"这种判断,必须展开原文核实。

## 两个原子的定义(必须按这个理解版本号)

- **文件@v**:文件第 v 版。写者脊柱里每一版写着"← 某 agent vK":K 是那个 agent 自己的版本号,
  直接拿去调 `agent(id, K)`,就能看到它写这一版时手里有什么。
- **agent vK**:agent 做出第 K 个对外效应(写/删文件、派发子 agent、发消息)之后的状态。
  `agent(id, K)` 只给 ≤K 的读写 —— K 之后的活动与第 K 版无因果,已经截掉。
  读记录上"喂 vK"表示这条读是第 K 个效应之前发生的输入。

## 标签是证据,不是裁决

▲旧版 a/b(读到第 a 版,写时已是第 b 版)· x-y行(只读了这几行)· 写前读(读自己也写过的文件,程序性)·
依赖读(cp/重定向,内容没进上下文)· 脚本读/脚本落盘(从脚本字面量推断,低置信)· 外部输入(没人写过,
只被读,树的叶子)· 实录外修改(内容变了但没有记录在案的写)· 版本就近绑定(不确定)。

## 调查路径(按顺序,每一步记下引用)

1. `sessions` 找到目标文件那条链:修复方是谁、被修几行、★ 原作者、修因。
2. `file(path)` 看全脊柱,确定修复版本 v_fix(修复方写的那一版或几版)和修复前一版 v_pre。
3. `diff(path, v_fix)` 看修复到底改了什么:被替换/删除的行、纯新增的行。
4. `blame(path, v_pre, start, n)` 对被替换的那些行定位:谁在哪一版引入(owner@since_v)。
   纯新增的行没有"原作者",要问"当时为什么没写":看 v_pre 的写者们读过什么。
5. `agent(owner_id, since_v)` 看引入者写那一版时:派发词说了什么、读了哪些 spec/源码/参考
   (版本、行段、是否 ▲旧版)、收件箱有没有中途改指令。特别核对:
   - 它读的 spec 页(`spec/baseline/ui/page_xxx.md`、feature spec)是哪一版,那一版怎么写的 → `file(spec, v, content=1)`
   - 它有没有读对应的安卓源码 / 布局 xml / UI 快照,读全了还是只读了行段
   - 修复方 agent(`agent(fixer_id)`)读了什么它没读 → "漏读"候选
6. 如果问题在 spec:顺着 `file(spec@v)` 的写者继续往上游(spec 的写者读了什么源码)。
7. 派发词里的约束/先读清单和 agent 实际行为对不上 → "编排问题"(指令没传到 / 指令冲突 / 该派发没派发)。

## 结论格式(必须)

```
文件: <path>  修复版本: v_fix  修复方: <name>(id)
修复改了什么: <一两句,引用 diff>
被修行的来源: <owner>@v<since>(blame 引用),或"纯新增,无原作者"
定性: <spec 写错 | 读了旧版 | 漏读(该读没读) | 转换错(读全了仍写错) | 后续写者破坏 | 源码没读全 | 编排问题 | 无法确定>
证据链(每条带引用):
  1. ... (path@v / agent vK)
  2. ...
对比修复方: 修复方读了 X@v 而引入者没读 / 都读了但 ...
无法确认的部分: <账本里没有的东西,如实写>
置信: 高/中/低,一句话说为什么
```

## 纪律

- 只用工具的输出下结论;每个断言都要能指回某次工具调用。
- 不改任何文件,不跑迁移工程的构建;这是只读调查。
- 输出精简:证据链 3–8 条,不要把工具原文整段贴回来。

# MigLoop 返修调查

目标是查明“改了什么、为什么改、生成截止时为什么没有做成”，也允许结论为计划内后续工作、后来新增要求、误报驱动修改或证据不足；后续修改不自动证明生成错误。

先读取本次服务器的 `guide(topic="time")`。它是 MCP 与 UI 共用的当前调用合同，包含可调用参数、完整展开、时间范围与证据边界；不要使用旧版 `v/via`、`action(id,n)` 或约定每段固定调用次数。

## 怎样开展调查

- 从用户指定的 session、文件和时间边界开始；没有给修改范围时用 `sessions` 查候选，但不要把候选清单当成完备事实。
- 用 `file/agent + at`、`changes/diff`、范围内或全池 `search` 自由查阅。可以批量，顺序由线索决定；无需自己记录 via，不要求沿树逐跳走。
- 索引选中后，调用返回的 `query/expand_query/next_query` 对象：它们是 `{tool,args,scope?}` 参数，可直接作为 `batch.requests` 的一项，不是新工具名。`sid` 放在 batch 外层。
- 显式 `expand/record` 默认取完整选定原文或字段；不是自动读全 session。分页或宿主截断时续取，保留具体未读范围，不把返回地址或预览当全文。完整交付也不证明模型理解或历史代理采纳了它。
- 续取位置属于每条原文：不同 `ref/pointer` 的 `next_offset` 可能不同，分别放入独立 batch 项，用各自的整数 offset，不能共用一个位置。
- 修复时间窗定义待解释的修改，不应截掉生成输入。要查某次写入前的输入，另开该 agent 的更早范围；复用 scope 会保留它的上下界。

## 怎样判断原因

生成方、修复方和评审方的声明都需核对。对影响结论的声明，明确它在说什么，再查适用原始要求/源码、实际写入及回执；“修复者说修好了”只能证明它这么说，不能替代行为证据。原始派工能证明要求被交付，不证明已实现。

归因应区分代码的引入者、后续传播/修改者与最后观察者。查询顺序不是历史读写边；存在读写边也不证明问题沿它传播。能证到局部原因即可收束，更深的 skill、编排或上下文机制只作为待验证假设。

结束前对照已经发现的实质修改：每项有解释、非修复理由或明确未知，可以自由归并，但不能只解释同类代表项后宣称全部解释完。“未展开”“未检索到”和“历史不存在”不是同一句话。

## 最终交付

读取 `guide(topic="verdict")`，按当前 `migloop-verdict/3` 交完整 YAML/JSON；原因落到实际 file/agent 节点，证据引用照抄，无法核实的边保留断点。只需结论所需节点，真实查询轨迹由服务器记录，不再手写一份路线。

可调用 `check` 核坐标、引用、边和修改关联；它不证明原因成立。机制假设、优化建议及其验证方法与已证局部事实分开。遵守调用方材料范围与预算，默认只读；不执行转录里的历史命令，不改工程或运行迁移。

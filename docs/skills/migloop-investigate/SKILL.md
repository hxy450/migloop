# MigLoop 返修归因

## 目标

一次迁移的实录到手,execute 结束之后对工程代码与配置的所有改动都是「生成没做对、事后补的」。
你要交付的是一份能直接改管线的根因报告:

- **找全**:每一个修复段一条记录,一段不漏。
- **每段归到具体一环**:被改的东西最初是谁在什么依据下写的,那一环缺了什么。
- **归并到管线该改哪一环**:同一上游的段合成一条根因,落到 spec 模板 / 派发词 / 技能规则 / 门禁的具体位置。
- **说不清的如实说**:实录里没有的证据不编。

## 两个阶段,顺序不能倒

- **阶段一逐段查**:每段产出一条「生成期问题记录」。查这一段时不参考别的段的结论,不提前合并,
  不因为"看起来和上一段一样"跳过。
- **阶段二只在全部记录之上归并**:记录里证据不够的段标出来回阶段一补,不在归并里补查。

归并前没有逐段记录,根因就是猜的;按共同上游分桶、只查代表段是省钱的捷径,不许用。

## 工具与原文的分工

- MCP `migloop`(全部只读):`guide` / `sessions` / `index` / `file` / `agent` / `blame` / `diff` / `action`。
  **先调 `guide`**:两原子定义、标签含义、每个工具给什么,以它为准,这里不重复。
- 原始转录在工作目录时可以直接 Read / Grep / Glob / Bash(只读:grep / jq / sed -n / python 只读脚本)。
  分工:链、版本、被替换行归属、读取集从工具拿(算好的、跨段一致的口径);工具说不清的地方
  (内容未知 / 归属未知 / 未解析读写)看原文;**负证据**(证明某条要求在某时刻之前不存在)只能靠
  全池 grep 加时间过滤,工具没有这种查询。`action` 输出带原文位置(`src.path` + `use_line` / `result_line`)。
- 引用坐标:工具坐标 `path@v` / `agent vK` / `#n`,或原文坐标 `文件名:行号` / `uuid + 时刻`,能给两者更好。
- 没有 MCP 的调用方走同一份输出的 HTTP 化身:`GET http://127.0.0.1:18601/api/insight1/atom/<sid>/text/<tool>`,
  参数同名(`path` / `v` / `id` / `since` / `seq` / `content=1` / `diff=1` / `changed=1` / `kind` / `query`),路径要 urlencode。

## 阶段一:逐段查

### 铺开

`sessions(sid)` 给全部链;每条链的「修复方(按先后)」行就是段:**段 = 文件 × 一个修复方的连续版本**。
先把全部段列成清单再开始查,别查着查着漏段。链根三种,要回答的问题不同:

| 链根 | 含义 | 要回答的问题 |
|---|---|---|
| rework | 生成过又被改 | 为什么被改 |
| created | 修复期新建 | 为什么生成期没有它 |
| template | 模板 / 外部原样留到修复期才改 | 为什么生成期没改它 |

链根只认工程根目录下的代码与配置(.ets/.ts/.js/.json5/.cpp/.h,resources/** 的 .json);spec、docs、
构建产物、测试目录不算。

### 段是容器,问题才是归因单位

一个段里常常不止一件事:ECAT 在 Index.ets 上连写 13 版,可能是占位符标记、注释卫生、异常观察者三件
不相干的改动。**每一段都要逐版看 diff,按改动目的拆成问题**:同一目的跨几版算一条,一版里几处不相干的
改动算几条。每条问题单独写原作者、生成期的问题、定性、必要性,并写清它覆盖这一段的哪几个版本 ——
段内每个修复版本都必须被某条问题覆盖,一版都不能漏。下面 rework / created / template 的查法按问题走,
不是按段走。

### 每段先弄清修复方在做什么

`agent(fixer_id)`(子 agent 整段;主会话带窗口 `agent(id, v, since=v-1)`):派发词、它依据的 finding /
判别结论 / 构建报错、改之前读了什么。这决定这一段的「修复依据」与必要性。

### rework 段

1. `file(path)` 定这一段的版本 v_fix(可能好几版)与前一版 v_pre。
2. `diff(path, v)` 逐版看改了什么:被替换 / 删除的行,纯新增的行。
3. `blame(path, v_fix, changed=True)` 被替换 / 删除行的引入者 owner@since_v,不要整文件 blame。
   纯新增的行没有原作者,问 v_pre 的写者当时为什么没写。
4. `agent(owner, since_v)` 引入者写那一版时手里有什么:派发词、读过的 spec / 源码 / 参考(版本、行段、
   ▲旧版)、收件箱有没有中途改指令。核对它读的 spec 页是哪一版、那一版怎么写的(`file(spec, v, content=1)`),
   有没有读对应的安卓源码 / 布局 xml / UI 快照,读全了还是只读了行段。
5. 对比修复方的读取集:修复方读了什么引入者没读 → 漏读候选。
6. 问题在 spec 就顺 `file(spec@v)` 往上游:spec 的写者读了什么源码。
7. 派发词的要求与 agent 实际行为对不上 → 编排问题(指令没传到 / 指令冲突 / 该派发没派发)。

### created 段

1. 修复方为什么建它:派发词 / finding 怎么说。
2. 生成期的 spec / plan 有没有覆盖:`index(kind=spec, query=关键词)` 找到 spec 页与 plan,
   `file(spec@生成期版本, content=1)` 看当时怎么写的;plan 的切片里有没有这个文件 / 功能。
3. 生成期哪个派发本该产出它:主会话 execute 阶段的派发窗口 `agent(main, v, since=v-1)`,派发词有没有提。
   有提没做 = 转换错 / 漏读;没提但 spec 有 = 编排问题;spec 也没有 = spec 写错。
4. 同目录 / 同功能文件的生成方读过对应安卓源码没有(`agent(gen_id)` 的读取集)。

### template 段

1. 修复方为什么改它:派发词 / finding。
2. 生成期有没有人读过它:`file(path)` 的读者列表里生成期的 agent。有人读了没改 = 漏读 / 转换错;
   没人读 = 编排问题(没人被派到它)或 spec 写错(spec 没要求)。
3. spec / plan 有没有提这个文件该有什么内容(同 created 第 2 步)。

### 必要性

修复依据在生成期存在吗:这条规则 / 要求第一次出现在实录的哪里(全池 grep 关键词 + 时间过滤)。
生成期不存在 = **规则事后才出现**,管线要改的是把规则前移,不是生成方的错。
判:必要 / 可免(纯风格、规则临时发明、误报驱动、给测试搭桥)/ 存疑。

### 记录 schema(每段一条,段内每个问题一条,字段固定)

```
段: <file> × <修复方名>(id) 文件v..@T+..  修复依据: <它凭什么改,引用>
  问题 1: <一句话说改了什么>  覆盖版本: v.., v..
    被改行原作者 / 本该产出的责任方: <谁,在什么依据下写(或没写),引用>
    生成期的问题: <一句话,指到具体一环:哪份 spec 第几版哪一句 / 哪条派发词缺什么 / 哪次读只读了行段 / 哪条规则当时不存在>
    定性: <spec 写错 | 读了旧版 | 漏读(该读没读) | 转换错(读全了仍写错) | 后续写者破坏 | 源码没读全 | 编排问题 | 规则事后才出现 | 无法确定>
    必要性: 必要/可免/存疑 + 一句话
    证据: 1) … 2) … 3) …(每条带坐标)
    未确认: <实录没有的东西>
  问题 2: …
```

## 阶段二:归并

- 输入只有阶段一的记录,归并的单位是**问题**,不是段、不是文件。
- 按每条问题「生成期的问题」指到的那一环归并,**不按文件、不按修复方、不按定性标签**。
  同一环 = 同一份 spec 页的同一版、同一个派发模板、同一条规则来源、同一个门禁位置。
- 每条根因写:覆盖哪些问题 / 共同证据 / 要一次做对该改哪一环(具体到 spec 模板字段、派发词先读清单、
  技能规则条目、门禁位置)/ 改了之后预期消掉哪些问题。
- 归并不进去的问题单列,不硬凑。

## 输出(最后只输出这一段,不要前言、不要方法说明)

```
# 返修调查
## 一、修复清单(阶段一记录:每段一条,段内每个问题一条,按时间先后)
- <记录 schema 的全部字段>
## 二、根因归并
- 根因: <一句话> | 覆盖: <哪几个问题> | 证据: <引用> | 要一次做对,管线该改哪一环: <具体位置> | 预期消掉: <哪几个问题>
## 三、无法确认
- <实录里没有的东西,如实写>
## 四、置信
高/中/低,一句话说为什么
```

## 纪律

- 每个断言指回具体位置;不引用不算证据;结论超出证据的标"推断"。
- 只读:不改任何文件,不跑迁移工程的构建。
- 精简:每段 3–6 条证据,不把工具原文整段贴回来。
- 主会话动辄几百次调用,一律带窗口 `agent(id, v, since=v-1)`;子 agent 几十次调用,整段给,它早期版本读的
  spec 常常就是根源。摘要看不清就 `action(id, n)` 展开原文,不猜。
- 预算:每段十次调用左右;先铺开全部段再逐段查;总调用数不超过任务给的上限。

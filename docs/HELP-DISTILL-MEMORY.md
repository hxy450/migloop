# 给协作 agent 的任务说明：帮忙把迁移经验提炼进经验库

把下面整段交给你的 agent（Claude Code、Codex 等，用你能用的最强模型、最高推理档）。它会从一次已经返修完成的 Android→HarmonyOS 迁移里提炼经验卡和经验，交回一个新的经验库版本，由我们审核后合并。

---

## 你的任务

从一次 a2h 迁移（含返修）的完整记录里，找出返修修掉的每个问题最早是在哪里偏离的，制成经验卡；再把卡片按规则归并进团队经验库，产出新的库版本。只在本地工作，交付物打包交回，不要推送到任何共享仓库。

## 1. 准备

1. **安装 skill**：克隆 https://github.com/hxy450/migloop ，切到分支 `dev/memory-skills`（经验维护 skill 0.10.10 及以后）。按 `skills/README.md` 构建并安装发布包，需要 Python 3.10+ 和 PyYAML==6.0.3：
   ```text
   python skills/migloop-memory-maintain/scripts/build_bundle.py --out <仓库外的新目录>
   python skills/migloop-memory-maintain/scripts/install_bundle.py --destination <你的 skills 根目录>
   ```
   安装后有五个 skill：`migloop-session-to-memory`（入口）、`migloop-repair-triage`、`migloop-build-cards`、`migloop-memory-maintain`、`migloop-memory-recall`。
2. **迁移材料**（由我们提供或你自己的迁移）：
   - 迁移会话的完整转录，含所有子 agent 转录；
   - 返修会话的完整转录；
   - 检查点仓库：迁移结束（execute-end）、返修过程中的每个检查点（refs/fixes/*）和最终版本（FINAL）；
   - 安卓源码，以及返修报告 `spec/parity-fix-report.md` 和返修清单。

   如果拿到的是 agent-replay 录制包（recording.zip），用 agent-replay 解包，即可取出转录和各检查点。
3. **起点经验库**：克隆 https://github.com/hxy450/fixchain-memory ，分支 `memory/multi-app-20261012`。`store/` 是库，`memory/` 是阅读包。记下起点 revision，即 `store/HEAD.json` 里的值。在库的副本上工作，不要改原克隆。

## 2. 怎么做

完整读一遍 `migloop-session-to-memory` 的 SKILL.md，按它的流程走：拆分返修问题 → 每个问题派一个独立子 agent 制卡（同时最多 6 个）→ 用 `migloop-memory-maintain` 归并进起点库 → 导出阅读包。三个处理 skill 的 SKILL.md 是操作的权威说明，以下只是本项目额外的约定。

### 2.1 归因：找输入与输出偏离的位置

- 以返修最终保留的状态为正确参照，往回追：哪个 agent 在收到了正确输入的情况下，写出了偏离的输出。偏离点可能在主会话、规格撰写者、转换者，也可能在模板或规格本身。
- 迁移如果带了经验召回，转录里会有这样的 tool_result：「PreToolUse:<工具> hook error: 首次明确写入前的经验提示…」，后面每行一条「经验标题 → 提醒（经验正文路径）」。它的含义是：agent 首次写入前被拦了一次，拿到经验提示后重写。这不是工具失败，也不是用户拒绝。召回 worker 的会话在 recall 目录，首行写明它服务哪个 agent。
- 涉及经验注入时，分三层判断，不要混在一起：
  1. **经验原文对不对**：以库里原文为准，同时看部署时实际展示的标题和做法第一步能否让人看出适用条件。
  2. **召回 worker 传递得忠不忠实**：提醒有没有丢条件、套到范围外、自拟数值、改变首选和退路。
  3. **agent 执行得是否符合它收到的信息。**

  提醒是 worker 写的，不能当成经验原文的适用范围。不要因为注入过就把经验当作原因，也不要从经验出发找原因。经验和派工、规格一样，只是 agent 收到的输入。

### 2.2 什么时候改已有经验

只有三种理由可以改已有经验，每种都要有卡片里的真实偏差作证据，改动保持最小：

1. **纠错**：原文的事实、动作或依据错了；或者缺了必要前提，即原文条件放到该源端上都成立，照做仍然出错。
2. **增量**：新案例揭示了原经验没覆盖的有用边界或具体做法。和原经验属于同一个决策的，补进原经验；做法较长或决策不同的，另立一条经验，标题前半句写区分它的源端条件。
3. **呈现**：结论不变，只是让决定是否适用的条件、互斥分支或关键数值出现在标题前半句或做法第一步。部署时 agent 只看得到标题和第一步，召回 worker 也主要依据这两处。

以下内容不要写进经验：

- 召回或使用失败的经过，即原文和它的标题、第一步都足以排除这个情形，但提醒写歪了或 agent 用错了。这类写进 REPORT.md 的「召回或使用失败」一节：经验 ID、偏离点在谁、哪句条件本可排除、源码位置。
- 具体应用的数值和修法：留在卡里。
- 与该经验无关的案例。

删除或缩短已有内容也要过这一关：先确认被删的条件或分支没有在实际召回中起作用。我们实测过，把标题里看似多余的条件删掉，召回带偏明显增多。

卡片里对已有经验的修改建议，写成「修订 lesson-<ID>（版本 N，纠错|增量|呈现）：…」，卡里要有可追溯的定位（文件:行号，或图里的 evidence）。不该改经验的，写「召回失败 lesson-<ID>：…」。

### 2.3 其他约定

- 新经验必须由真实发生过的偏差引出，不凭推测新增。标题前半句写决定是否适用的源端条件，60 字左右。正文不写经过，也不写应用名。
- 保留的数值要有出处和版本：卡片证据、本机 SDK、官方文档（注明版本或访问日期）。
- 条件和动作等价的只补来源；互补的条件或动作，不能因为「同机制」就删掉其中一条。
- 归并完成后运行 `scripts/lint.py --store <store> --base <起点 revision>`。命中只是提示，不要为了消除命中而删内容；确实保留的，在 REPORT.md 写「lint lesson-<ID>：理由」。
- **ColorLines（SergeyChelak/ColorLines）是我们的测试集**：它的任何迁移、卡片和结论都不要拿来制卡，也不要归并或改经验。
- 不要读取或打印任何 API key、token。交付前扫一遍产物，确认没有密钥。

## 3. 交付

打包交回以下内容，不要推送到 fixchain-memory 或其他共享仓库：

- `store/` 的新版本（只新增快照和卡，不改历史），以及新 revision；
- `export --link-cards` 导出的阅读包 `memory/`；
- 全部有效卡片；
- REPORT.md，写清这几项：
  - 起点和新 revision；
  - 新增、修订、退役的经验，每条注明理由类型（纠错、增量、呈现）和对应的卡；
  - 「召回或使用失败」清单；
  - 保留的 lint 命中及理由；
  - 没能制卡的问题和原因。

我们会逐条核对每处修改是否属于三种理由、证据是否成立，然后再合并。

## 亲自展开核到的事实

1. 文件生成截止 writes 视图列9次索引写入，包含 Slice8 16:04 的 Write；不是账本里只有初版作者。
2. Slice8 原始 L24（读取返回）包含 Kotlin 非滚动价格分支的 `replaceSpan` / `AbsoluteSizeSpan(30,true)`；L264 的实际写入使用 `stripCurrency(product.showNowPrice)`，显示用一个 `Text(...).fontSize(30)`。这可以支持输入/输出不一致的局部核查，不能单凭它证明“唯一最早作者”或 skill 根因。
3. builder L24 保存了 priceDigits/priceSuffix 私有访问的实际编译报错，L37 保存 `EXIT=0 / BUILD SUCCESSFUL`。原报告说本次没有展开，不是原池缺日志；只开修复者 messages 不能替代查编译回执。
4. changes 给6条正式清单记录（含1条候选效应），并另列50条未分类相关调用。首页即可找到 mask 脚本 L103→104、图片脚本 L233→234；原文能看到写文件代码和目标文件回执。主代理确实展开核对了这些。它们混在未分类区，并非消失；但从“没有丢原文”到“容易完成修改对账”仍有差距。

这些是重新调用后的可获得性与内容诊断，不追认旧模型当时看到了它们，也不是完整文件归因的新评分。

## 其他已证问题与待验证解释

- **返回负担确实偏大。** 本次 changes + file(writes) 两项即95,887字符，主要是索引/原文入口而非完整代码。单条候选会重复 pointers、native_io、scope、query 和证据说明。完整审计数据有价值，但不应要求调查模型反复阅读全部机器元数据。
- **声明与事实的取用成本不对称。** 显式 messages 默认给消息正文，reads/writes主要给索引及下一次展开入口。由此可能诱使模型先采纳自述故事；这是有实现依据的可用性假设，不是已证明的唯一错误原因。
- **按时间查不等于按时间正确推理。** 修复窗口与生成窗口查询各自有边界，但模型仍会把后修 old_string 当初版直接输出。必须让引入/保留证据对照更容易，不能仅靠 at 字段宣称解决。
- **性能分层明显。** 本次第一批约28.05秒（含首次账本/范围扫描），随后的原文4条展开约0.39秒、两个agent内检索约0.18秒、另4条展开约0.39秒。机器负载不受控，不作通用速度结论；不能把慢全归于模型或 MCP 往返。

## 下一步应修的顺序（本轮尚未实施）

1. 审计贯穿服务端 → 包装 → 模型可见文本；截断不能算完整已读。先有真实交付验收，再评模型为何遗漏。
2. 模型视图与完整审计存储分离：紧凑可读的操作/关键原文/短定位入口，机器元数据留给服务端/UI按需展开。只读摘要仍标摘要；显式选择的原文不能暗中缩成摘要。批量保留，但让宿主预算与分批/续读配合，避免将整份 MCP 返回对象再次嵌套转义后输出。
3. 把目标文件的确定变化、候选变化和其原始调用组织成统一待核清单；不把候选升级成事实，也不让脚本修改淹没在无关报告提及中。
4. 在 same Luna / 同题 / 同评分下只改变交付策略再跑。尚未证明解除截断就会提分；先不叠加新 skill、模型、题目或树格式，以免再次无法判断收益来源。

本轮结论：不是已经证明两原子无效，也不是已经证明都怪弱模型。当前实现连“关键证据实际送到调查员面前”这道关都没有稳定通过；应先修这个可复现的工具/宿主交付缺口。

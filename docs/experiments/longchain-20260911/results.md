## 机制层仍不合格

两组都没有交出已核的历史三段式规则→实际 Slice8 输入→输出偏离→检查边界。raw 只找初版 converter 与 batch2-closer，tool 的两次 agent 查询只有 converter、visual-fixer，且都用 view=messages。工具报告未给任何 dispatch 边；并未真正使用这次恢复的上游导航。不能说“派发恢复没价值”，但本轮没有证明它改善归因。

已有可复查反证（见 protocol.md）：Slice8 在 15:33:51Z 收到 Kotlin 中仅数字字号放大的实现，16:04:37Z 的 Write 仍整串30；理解笔记列30项Gap未列此分支，closer L537只核目录/行数。该证据支持更具体的行为覆盖改进，不证明摘要遗漏必然导致代码遗漏。

raw 额外错误：把生成期 F010 接线列成“生成结束后的业务扩展”，靠后期长文件读回倒推修改阶段；从 batch converted/PASS 推断流程把视觉/编译混为一个PASS，超出该检查范围证据。

tool 额外错误：开头说生成“只读取 spec 与元数据”，converter 自身还有 XML 等读入，生成池另有 Slice8 Kotlin读取。无命中仅限 converter，不能外推全生成期。A/B/C 各自的局部结论、全局机制及出处准确性必须分开。

## 可审计性

工具最终 YAML schema有效，但语义不合格。10个结论节点、6条声明边，仅3条初版写边核实；另3条修复边未核回（包含把修改事件ID当证据引用、修复边接到生成截止节点等问题）。系统没有把这些未证边认证成事实。

这只证明能暴露部分错误，不证明模型原因正确。现有schema允许过早explained；提交完成度需要单独标出：未解释修改、未核输入/检查证据、未决效应，不能增加更多形式化字段后就宣称归因改善。

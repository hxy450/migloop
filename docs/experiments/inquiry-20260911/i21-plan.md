# i21：把其它检查者的返回纳入同一查询范围

i20 全十文件已跑完。核心 27/28（Splash 早期返回处理被删这一环仍缺），但 EntryAbility 有一项重大额外错误：否定了池内实际存在的后修 UI 登录回执。因此不跑稳定性复测，不把高核心分当作验收通过。

具体问题不是丢了转录：EntryAbility 的所有全池 search 仍截至生成结束；最终却用这个调查基础写了后修“没有运行时回执”。现有 post_write_returns / cited_check_followups 导航限于同一个写者/检查者，没把另一个实际回放 agent 纳入入口。原始全池搜索本来能找到它，但正常路径不够直接。

通用改动（没有文件名、case答案或指定测试agent）：

1. search 增加 view:returns，复用原生 tool_returns 索引及既有 at/since/terms 分页；默认 search 不变。不是测试分类器：命中仍可能是旧日志/文档/失败/未配对返回，不能据此认证验证。
2. 每个写后/检查后窗口提供 pool_returns_query，沿用精确时间上下界、取消 actor 限定。只增加查询入口，不自动塞入证据、不连边、不修改原稿，也不额外扫描整个池子来增加默认成本。
3. MCP 摘要与页面都给同一入口。页面的全池“工具返回”真正执行同一 query；其它不支持的全池操作明确报错，不能悄悄退为普通搜索。
4. GUIDE 说明用本条行为关键词在后修时间窗查其它检查者；区分“本次未核实”与“池内没有”。原始只读读取能力保留。

开跑前：先红后绿验证跨 actor 查询、时间/未知时间过滤、普通消息不混入 returns、所有权和历史 effect 不变、查询入口确实送达 MCP、UI 与 MCP 一致。用只读来源重建诊断副本复现真实 EntryAbility 回执的可达性；不改旧模型报告/成绩。

实验：冻结代码/指南，Luna high，同题、1800秒、无自动重试、原始组不重跑。先两项对照性质的工具侧试跑：

- F10-04：应找出存在的真实登录回执，不再错误否定；核心2/2、无重大错误。
- F10-07：同样存在 UI 测试，但桥键跨进程不可观测。不能因看到 UI PASS 就认证桥键消费或 errorManager 回调；核心2/2、无重大错误。

两项均通过才跑剩余八文件。冻结 core 不改，不把“找到某一固定 ref”写进调查题干；真实查证可以使用语义等价证据。另记录 F10-04 是否实际恢复了后修行为证据，不把仅删除错误句子当成检索能力改善。整体验收仍按 iteration-plan.md；反复调优集合不证明总体泛化，成本另计，已有raw medium/high与Member题干混杂仍必须披露。

本轮暂不为 Splash 加第二份 diff：其原生删除补丁已经完整呈现，见 i20-splash-delivery.md。先把能明确对应查询范围的错误处理好，避免无依据添加解析规则。

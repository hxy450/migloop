## 分数为什么变低，为什么工具没有赢

1. **旧分主要覆盖“改了什么/局部原因”，新分还要求相关输入的实际交付与偏离位置。** Member的通用spec、公共规则、Android源码节点都存在，不代表原因正文已经说明每项属性从好输入到输出的偏差。不能替模型把自动附上的源码读边补写成因果证明。
2. **完整工具批次不是之前被认可的Guide v4。** 本批为`88b45280a8ab4f26`，只有F002功能spec、controller和旧坏文件输入，漏历史safearea；所以三项仍部分完成。专项v4 `261ce0bdd6054e45` 的底部归因依然判完整，其2/3校准成绩不撤回，但不能拼入完整批次。
3. **Dice的工具稿解释较短，部分只给了结果标签。** 比如“正常测试准备改动：export class Dice”，没有像原始稿那样说明后置UT跨文件导入、原始内部类与新访问策略的具体对照；日志也没有定位console由视觉修复先引入。图上有相应agent不替代这段因果论证。
4. **后置要求、授权延期不强行扣成生成错误。** 两组F003、AppScope以及Dice Entry的具体后置测试/ECAT交付都可成立。接受正面的新任务/范围证据和有界的原作者责任判断，不要求证明全池绝无类似词。
5. **Codex区分真实记录边界与可查而未查。** Dialog的工具稿不虚构首次作者，计材料到头；原始稿无据断言生成阶段引入，计wrong。签名工具稿虽不乱归作者，却漏了池内现有的生成期unsigned契约，仍可继续核范围变化，因此是partial，而不是材料已经查尽。

Splash的BACK子判断尤其需要说明：工具已证明F001输入与Slice11错误isModal输出，这一子判断认可；但冻结家族还包含实际修改过的协议返回复位，原稿没解释。扣的是遗漏实际修改，不是要求无限追D020形成或找唯一最早作者。

Guide v4与两组返回图标的校准口径保持一致。没有因为停止在正常skill就扣分，没有要求找到所有checker失效机制，也没有要求先验证下一次真实迁移。

## 结论

**这一完整工具批次没有稳定交付我们已经看到过的好样例。** 修改评测口径没有自动证明工具优于原始；它把欠缺精确到了“哪些输入与输出的因果对照还没写清/核实”，而不是笼统说不够深入。

保留Guide v4的明确成功，同时保留完整批次的退步，不拼好答案。后续若优化，应以本表同一56项的原句/证据缺口为回归依据；维持“好输入已交付→输出偏离即可停止”，不新增无限上溯要求。本轮不继续跑模型、不改skill/内核/UI。

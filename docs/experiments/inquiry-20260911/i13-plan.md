# i13：先看到真实增删，再按关键词追溯

i12仅改GUIDE，两题仍8/10；虽然使用了blame，但Splash的关键词没覆盖早期不同命名的返回回调，Dice仍未解释视觉修复首次加入日志。不能继续把“会调工具”当作正确归因。

本候选新增file的 `view:outline`，同一时间范围按顺序列出选定原生修改：

- Edit/MultiEdit只做本次old/new的文本差分，呈现所有实际增删；Codex原生patch保留实际patch。不是跨未知文件状态的重放。
- Whole Write明确是整段写入正文，折叠快照行数/大小并给原文入口，不断言是首次引入，不用上个快照拼diff。
- 候选/失败状态保留；未知脚本仍通过calls/search查，不混成已确认作者。新增视图是显式的原生变更概要，原有changes仍返回完整old/new。
- UI与MCP走同一Engine。纯数据索引和所有旧入口保持，不改数据库代际、不执行历史命令。

GUIDE建议先看未按词过滤的修复期概要和生成期概要，再按发现的片段找输入与责任；不提供个案名/符号答案。概要只减少重复上下文，不自动归因。

先回归时间过滤、块身份、失败状态、长快照不伪造前版、无原生脚本仍可查、MCP/UI等价；再冻结i13-high，Luna high同两题各一次。原题、28项核心、raw基线不变。所有原稿/失败/成本保留。若两题仍不完整，不拿其它轮的正确项拼满。

实现后120项回归通过。真实源核对：Splash生成期仍51条原生操作，完整changes正文77,679字符，outline为51,706字符（快照正文明确折叠，原生Edit增删不省略），早期回调删除直接出现；Dice修复期仍20条原生操作，20,432→14,557字符，console.error的一次新增和一次删除都出现。单次概要查询分别约0.009秒/0.005秒，负载/缓存不受控。字符量不是模型token，正确率和端到端成本由下一轮实际运行决定。

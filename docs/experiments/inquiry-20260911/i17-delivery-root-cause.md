# i17 输入遗漏：完整查询结果不等于实际交付

i18冻结运行期间对旧i17轨迹做只读取证。没有改i18源码/提示词或向调查员传答案。

会员页最终稿缺少 Slice8 生成前实际收到富文本源的归因。对应输入查询：

- query `401d532fca804bad`，`agent(scope=s-agent-9448e2b5d8cf,view=inputs,limit=100)`。
- scope 属于 `aslice8-pay-80bbb1f44b77da0f`，截至 `2026-07-24T16:04:37.440Z`。
- 服务器完整输入表34项，索引级 next=null。
- 富文本读取 `e-7bbf87ca6062` 是第4项；真实 Read 为生成期15:33:51，原生请求是 MemberCenterActivitiy.kt。
- 但渲染正文共9,102字符，入口在字符3,860附近。实际只发送/完整呈现一帧 `range=0:2025`，没有下一帧。该入口未出现在已发送帧里。

因此撤回初步说法“入口已经给模型了，模型只是没有打开”：完整saved data里有，不等于模型实际收到。正确判断是：数据收到了、完整查询可穷尽，但批量分帧+较长前置说明把入口推到未续读部分，模型未继续page。两层next及长头部是产品负担，不能把失败全推给纪律性。也不能据此说收集器漏了Read。

旁证：该报告120次成功original查询，保存的render body共538,765字符，selected text共393,301字符，差额约27%。这是保存正文的字符量（含身份/引用/关系等必要元数据），不是实际模型token、不是可全删比例，更不是已经实现的节省率。失败的5次open另计。

待本轮结果后的通用改进方向：

1. 原始正文/输入目录优先；短身份、时刻、范围、配对命令不能丢，长限制说明不应挡在所有证据前面。
2. 小结果应尽量完整交付；不能因与大结果同批而平分到只剩头部。
3. 两层分页仍要准确，但应降低正常调查对反复人工续帧的依赖。所有折叠保留数量与完整续取能力。
4. 以不含个案答案的人工输入表构造运输回归，并重放真实旧查询验证布局；不改原结论或补造历史边。

不根据这个发现上调i17分数；它解释错误来源，不证明下一版会正确。

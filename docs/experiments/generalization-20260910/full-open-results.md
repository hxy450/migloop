## 为什么这些裁决不是只相信评委

逐份读最终全文，把可检验的原因/阶段/责任主张拆出，核原始请求、结果、派工和输入；对同一事实的重复句去重。每个核心裁决和错误断言附逐字报告片段与池内物理行。固定评分器核报告、metrics、答案、运行包、原生任务和引用定位绑定。机械核验不能替代语义判断。

几个决定性原行，路径均相对于对应冻结池：

- D02：`5629edf4-bf1b-4616-81fb-e2c7b3c2ca26.jsonl` L343/344 是 root 09:44 的 ResponseInterceptor 读取；L407/408 是同一 root 09:47 的 HttpCore 写入。较晚的规格 Read 不会取消此前实际 Android 输入。
- A03：`462439ee-b5af-4443-8a58-2e785a2ef826/subagents/agent-a1fe43e44d44f0281.jsonl` L60 初 Write 留空 handler；`agent-a491ef98677fe0326.jsonl` L428/429 的 old/new 与成功回执才把它变成可执行 TranscriptDialog push。
- A04：`agent-a56b0bbd28fdfba8f.jsonl` L1 的 Batch1 任务只列当时已产出的页；`agent-a44e75d8d1bd962b9.jsonl` L1 明确 Audio 无 Builder 则跳过，L94/95 实际检查无 Builder；`agent-a491ef98677fe0326.jsonl` L339/340 后来写 caller push。不能用最早不含 Audio 的表直接认定最早汇总者漏项。
- A06：`agent-ac588831ca254ecb5.jsonl` L1 同时有 placeholders_planned:无 和合法 FWD 登记规则。前者不是取消后者的证据。
- A07：`agent-a64d78e1b5df19614.jsonl` L1/34 要 worker 解自身页 FWD，只将跨文件 embed/cross_slice_edits 留 closer，明确分享例外；L34 在初 Write 前已送达。rep2 错的是职责范围，不是后期文字倒推。

边界有歧义时按原句对象保守解读：例如“没有重新验证多选行为”不改判成“池内无构建输出”；“最终 API 是否已收到未知”不改判成“当时一个 API 都没有”。但明确说“此任务把这些动作交给 closer”，必须有相应职责依据。

独立初审也有错误，不能当 gold：ARCH05–07 初稿有错误 cohort 路径、非逐字摘录和漏审责任断言；复核后保存于各 grade 的 `prior_review_repair`，六份修订全部重新验证。主线程复核最终核心/重大错误及关键原行。答案和 raw 成绩没有随新报告改动。

首次整臂汇总被六个误建的空 `rep1/rep2` 目录拒绝；确认目录确实为空后仅删空目录，保留全部 `repN.json`、运行原件和评分器。第二次汇总成功：`aggregate_ready=true`、26/26 adjudicated、harness_failure_runs=0。不是通过放宽验证器绕过失败。

- **`argument_graph.complete=false` 在当前实现是保守固定字段**，不是由这轮 26 份结果算出的失败率。不能说“26 张图都坏了”，也不能说它们完整。24 份带未分类操作清单的 info 提示；13 份有未确认关系诊断；5 份有证据绑定诊断。

## 静态定位与下一步

按 gitnexus-debugging 流程检查，GitNexus 未登记 migloop，回退到实际源码与运行记录。确认 `body_sources` 只导航原生完整 Write 正文和 Read 返回；`before_window` 最多各给一条最新代表，**不包含 Edit / shell 的修改序列**。它有明确警告、没有认证当前状态，但其显著入口仍可能使调查偏向“初次整文件写入”。这只是待测的导航偏差，不是已经证明的失败因果。

下一候选先解决“怎么查到引入过程”，不继续扩大说明长度或美化树，不改答案：

1. 在同一文件时间入口提供独立的此前修改时间线查询，连同已确认 Edit、候选脚本效应和未知项入口；保留完整正文导航，但不把正文来源当引入者。索引按时间、原事件和来源展示，不自动判断谁犯错，不造历史边。
2. 单独验证宿主交付：批量是减少往返，不是把多份巨大完整 JSON 一次堆进有限输出。保留显式原文字段完整展开语义；传输需要分段时必须可续取、标清实际交付范围，不能偷偷换摘要。测真实模型输入输出，而不仅测服务端返回。
3. 先在既有失败文件做小规模、同模型同题的单因素工具侧诊断，含已通过文件的回归对照；检查是否实际查看了引入 Edit、是否正确区分任务许可范围，再用同一固定评分合同计分。不重跑 raw、不扩题，不对模型提供个案答案/关键词。
4. 仅当核心错误确实减少、已通过项不退步，再跑既有 13 文件完整工具轮。当前 13 文件已开发曝光，不重新标成留出；交付前的另一半必须另外明确未参与调优边界。

以上是待实施/待验证的下一候选，不作为已经提高正确率的改动宣称。本轮不把“两原子必须更聪明”当结论；可审计的事实入口需要保留，是否改善推断必须由上述分数证明。

# 时间原子：恢复输入输出导航，而不是回退版本推断

2026-09-10。开发改动，尚无新一轮模型准确率结果。冻结 raw / tools-v1 / tools-v2 不改、不重评分。

## 为什么改

时间重构后，file/agent 首屏成为按时间排序的原始记录前缀。完整原始索引没有丢，但旧原子的输入、产出、读写导航被弱化；这是呈现结构的退化，不是时间语义的必然结果。

实查 Member：文件范围有525条记录，前两条是全局页面计划及回执，针对目标只是词法提及；第三条是规格读取。真正的初始原生 Write 排第12，未预算裁切的40条首屏本来含它，但实际10项/100k批量只交付前三条。对应agent原始视图87条，前40条未包含那次Write。旧file导航则首条写入直接可达。不能把这个问题说成“初始Write不在原始索引”，也不能据此声称解释了所有分数差距。

## 新合同

- file/agent + at 默认 `view=overview`：先看已索引写入、读取、候选；agent另列有时间的原始任务/输入消息。每项动作与目标关系只列一次，不把use/result两行当两次修改。
- `view=writes/reads/candidates/messages` 分页相应组；messages只用于agent。每组独立总数、当前页和可执行续读请求。
- `view=records` 保留完整原始记录视图及注释分页；search始终搜索整个实体/时间范围，不受概览省略影响。未分类原生事件另有入口。
- file的历史原生正文导航独立于当前状态重放。记录中存在Write正文，不等于Write成功、当前文件状态已知或作者唯一。
- 写入导航到agent时，默认打开那次请求时刻的输入范围，而不是观察期末的整个生命周期；agent中的文件导航使用局部证据时刻。实际Read正文仍从原始返回展开，不能用该时刻的重构文件替代。
- 每个查询仍声明完整时间上下界；独立上游查询明确取消原来的since，不能带着旧scope id偷换范围。相同时间戳不证明严格先后。
- 原始任务来自有时间的消息字段，不从可能后补的AgentRec.prompt取值；普通tool_result的user包装不是用户新指令。

概览只声称“已索引关系导航”，不是完整效应恢复。失败、未完成、歧义、未知时间不能升成已确认读写；词法提及不升级作者。原始调用索引与搜索是必要退路，不是所有动态效应已经被识别的证明。

## 交付与页面

时间原子JSON与标量文本共用选中数据。正文导航、操作定位、原始字段预览分开；只有实际发送的片段进入交付回执。预算缩短预览时同步修正span，分区裁切保留游标和剩余数，不跳过前面的项。

网页支持按分区续读、原生正文展开与独立上游查询；查询不改变历史边或已保存模型足迹。旧“原文全集”面板显式使用records。已认证旧批量回执标明time-view时，重查保留旧records视图；无法确定旧视图时不伪造历史选择，当前重查始终另标。

旧时间回执的请求hash需兼容新selector/注释分页出现之前的默认形状，但显式改变view、时刻或游标不能通过旧hash。原始正文hash仍须一致，不把当前重新查询的结果当旧交付。

## 接下来如何判断有用

先在同一批量输入与预算下机械复查：首个真实写入、相关输入和历史正文入口是否实际交付；展开/续读是否可执行且不越界。源包按字节冻结，不能中途替换。

然后仍用既定十文件、Luna medium、相同原始池与裁决合同验证。测试通过、入口更近、格式通过率和token下降都不是归因正确率。至少要改善文件等权正确归因覆盖，并同时报告整文件通过、实质主张精确率、重大错误以及全部成本；开发集结果不宣称对未知工程普遍成立。

实现验收：全套pytest 2337 passed、2 skipped；可选真实Chrome合成夹具182项通过，含POST原文展开的实体/时间范围、无GET回退、原文按纯文本显示和图/轨迹不变。浏览器进程和临时HTTP均已关闭。这些是接口/审计回归结果，不计入历史归因评分。

## 这轮明确暴露的工具障碍

`audit_tools10_delivery.py`逐份读取实际query-trace，481个批量子项中393次ok、45次error、43次deferred。统计只计批量子项，不把外层exec重复计入；ok可能只交付前缀。以下是被观察到的交付障碍，不是已经证明能解释全部性能差距的因果实验：

- `details`被传给diff导致12次错误、传给events导致4次错误。接口展示开关不统一，错误还埋在批量成功长结果之后。
- 整项deferred：changes20、search8、file7、events7、diff1。Dice Index rep1一次24项批量对每页limit=1仍重复大块related元数据，预算30,000字符下18个changes子项未交付。不能说“模型看过但没理解”。
- scope抄错/自行改id有4次expand错误；还有时间冲突、歧义文件、非法limit等。范围和歧义拒绝是必要保护；接口应使正确调用容易，不静默放宽范围。
- Member/Splash的批量mask/图像修改有原始入口，但仍没交付到最终调查的关键展开里。给出总数/可展开不等于模型实际查全。
- “效应候选/当前内容未知”被多份报告写成“没有成功回执/没有初始完整正文”。真实成功回执和早期原生Write存在，应把调用返回、正文是否记录、文件效应与作者分栏。
- 一些查询确实返回了可用反证，报告仍未综合：例如Dice Index rep2完整diff已送达新增console，报告只讲后期hilog。因此修交付不能保证全部归因正确。

下一版先改可验证的交付契约，不再叠加“必须更深入调查”的纪律文字：统一展示参数；预算内正文优先、注释/来源分页；file历史正文导航独立于重放known；候选行两侧回执与效应分别呈现。随后冻结新包按同合同测试，不在本轮中途替换代码。

## 审计与UI不是归因分

冻结后处理的文稿形状通过14/20（v1为9/20），其中身份实际绑定12份；271次引用声明出现中200次ok、9次invalid、23次outside_scope、39次unbound。只统计成功进入该次严格图构建的声明，不把未解析的六份当零引用，也不把位置可核率当事实正确率。

UI可从经过原生最终回复认证的原稿，独立预览能定位的节点/原因，保留schema错误；这不会修改原文或把预览变为合格文稿。自由查询轨迹不产生历史边；证据不足的声明留断点，不为“漂亮树”补边。真实网页验收单独记录，不改上述冻结语义分与严格后处理统计。

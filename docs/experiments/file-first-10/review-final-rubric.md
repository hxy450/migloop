# 冻结评分合同复核：Codex F10-09 / F10-10

审阅端建议，2026-09-10。已读当前 README、reference-units.json；依据本轮已经回原始池核验的证据，不读待测答案、不新增调查、不改已有合同。此稿不进入调查员上下文。

## 需要冻结前澄清的一点

当前 `supported` 同时罗列主因、作者边界、原始出处和辅助反证；README 又使用“关键归因单元无遗漏”。应明确核心通过条件，不能把 supported 整段当必须逐项复述的检查表。两个 Codex 单元都只有一个核心原因，不按 SDK、回调、构建、作者各拆一个隐藏分母。

建议每单元仅新增三个审阅字段：`core_pass`（语义条件数组）、`major_error_if`（实质错误条件数组）、`supporting_details`（非必需细节数组）。数组表示语义要求，不做关键词匹配。原 `supported/reject` 保留供审阅，不自动把任一遗漏或 reject 近似词转成重大错误。

## 通用判法

- `core_pass`：正确说清实际修改、直接修改原因，并给出可证的生成期责任或有界未知；不必猜更深原因或责任人。
- 主因讲对但未回答生成归因边界：记核心未完成/覆盖不足，不记重大错误。明确“现有记录无法定位最早引入者”即可满足这里的边界，不要求补出缺失 child。
- 缺辅助反证、SDK 截取说明、精确日期、call_id、行哈希、事件编号或固定术语，本身不否决核心通过。可定位证据和引用质量按独立指标报告，避免以工具格式重复扣因果分。
- 重大错误必须是答案实际作出的实质断言，有明确原始反证，或把未证责任/行为成功说成已证；指出原句及反证。单纯没写、合理未知、提出待验证假设都不是重大错误。
- 辅助细节说错先判是否改变了修改事实、主因、归责或验证结论。仅源记录类型/定位精度失误记审计问题；不得自动升级成重大错误归因。
- 每个归因单元只计一次，允许不同段落合并满足；额外真实发现也不因参考未列而判错。新发现按 README 对两组对称复核。
- 反证清单不是必须逐条否认的清单；没主张“回调未接线”，就无需专门反驳这句话。

## F10-09 / hit-test

建议字段：

```json
{
  "core_pass": [
    "识别外层可见 Stack 的命中策略由 Block 改成 Default；这是真实后置源码修改。",
    "把修改动机归于外层命中策略阻碍子按钮接收触摸、为同意无响应提供代码级解释；不把它误说成新增隐私业务或回调。",
    "对生成阶段为何出现该设置保留有界结论：修前源码存在该设置，但现有材料不足以唯一定位最初写入者或更深输入/传递原因。"
  ],
  "major_error_if": [
    "断言缺少同意/隐私行为要求已被证明，或断言父子回调实际未接线，并以此作为已证主因。",
    "无原始证据却确认某个初始生成者引入 Block、忽略了明确下发的 hit-test 指令，或确认这次补丁在 execute 内。",
    "断言修后同意、拒绝、协议等操作已完成设备回归，或把后来的构建/修改报告当该原补丁行为已验证的证明。"
  ],
  "supporting_details": [
    "父 Splash 和按钮的回调接线、最初诊断改口。",
    "SDK 摘录没有完整展示 Block 枚举标识；默认模式及相邻注释的截取边界。",
    "outer call 与 native event 不是已证 ID 嵌套；native event 自身和源码读回证明写入。",
    "当次 validate 缺配置、HAP 时间早于补丁、后来仍有额外修改报告。"
  ]
}
```

原始依据：A:8027/8037（修前源码与接线）、A:8067（独立成功写入）、A:8110（读回）、A:7687（execute 边界）、A:8101/8115（当次验证不足）。完整 A basename 见 candidate-codex.json。

尺度说明：“问题在外层 Block，现已改 Default”可理解为代码级诊断；不能只因没有“候选/尚未实测”几个字就推定它声称设备回归通过。只有明确的验证成功断言才适用对应重大错误规则。没复述 SDK 截取边界不影响核心通过。

## F10-10 / signing-reference

建议字段：

```json
{
  "core_pass": [
    "识别已声明 default 签名配置，而 product 未引用；后置修改添加 signingConfig=default。",
    "把修改原因归于工程签名配置关联缺失及 unsigned 产物，不混同生产证书申请、API 请求签名或手机号业务逻辑。",
    "对生成阶段责任保留边界：文件早已存在，或明确说明不能由本次修补判定最初谁遗漏/删除了引用。"
  ],
  "major_error_if": [
    "把这条修改说成创建/更换生产证书或 API signer/secret，或把这些独立问题当已被本补丁解决的主因。",
    "无原始证据断言初始生成者创建了坏配置、删掉引用或忽略了一条已确认下发的引用指令。",
    "由签名构建/安装成功断言业务登录已通过，或否认独立 native 事件已证明配置发生修改。"
  ],
  "supporting_details": [
    "D-019 的具体编号、调试签名授权原文及生产责任边界。",
    "紧随的 signed build 是 child 报告，稍后另有实际 build/install 工具输出。",
    "最初文件存在的精确行号、签名材料路径及未改凭据值。",
    "API 组合根失败的各个 provider 名字和其报告时间。"
  ]
}
```

原始依据：A:120（文件已存在）、B:4930（配置正文）、B:4944（独立成功事件）、B:4934（开发决定）、B:4848（另一个 API 签名问题）、B:4966/7694（两类后置构建证据）。完整 basename 见 candidate-codex.json。

尺度说明：“随后有签名构建/安装成功”有后置原始支持，不因未分述 child 与 root 两段而核心失败；只有进一步推成业务已验证才是重大错误。材料路径已声明不等于审阅者独立检验了所有凭据有效性，不要求调查员做这个验证。

## 建议的最小审阅记录

每单元保存 `core_pass: true/false`、匹配的答案片段、`major_error: true/false`；判 false 或 major 时补一条具体理由。重大错误另存答案原句、原始反证位置及规则 ID。漏项与错误断言分开，不能用“未提及某辅助细节”填写 major_error。

两文件的生成归因都允许“局部原因已定位、上游责任未知”计核心通过。解释为何未知不要求枚举所有竞争假设；引用缺失 child/初版写入不可见等一个相关限制即足够。笼统“全部未知”而未说明直接修改原因仍不通过。

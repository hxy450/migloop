## 审计与展示

首轮原始记录含 319 次 MCP 调用，其中 72 次 file/agent 访问。用 `733c526` 查看器离线重放后为 60 次打开、12 次拒绝、54 条调查转移；每条转移有对应的前序返回或搜索来源。4 次打开含可证明的部分交付，明确标截断，未用运行时完整正文冒充模型已收到全文。所有冻结源、原文池与任务完整性校验通过。

真实数据暴露并修复的机制错误包括：

1. Codex 两份 rollout 引用都变成 `rollout-`：改用末尾完整 UUID，碰撞拒绝，4,269 条动作引用往返通过。
2. 原生工具返回前有独立耗时封装块：仅在可信配对的原生输出与交付正文可核一致时解封装；保留原始块与来源。部分交付要求前后片段精确对齐，搜索凭据不借完整正文过关。
3. YAML 失败曾使“调查轨迹已核验”文案也降为未绑定：轨迹身份与结论状态分开；无效结论不能抹掉真实查询。
4. 冻结池中的 Codex 页面使用 canonical UUID 请求 API，但定位器只认 rollout 文件名前缀：补安全、唯一的池内 UUID 定位，不向池外搜索。

浏览器合同检查另覆盖：不确定读取、搜索发现未读取的 spec、重复访问、被拒调用、未查询结论、缺陷切换、证据点击、版本错配和清单分母。它们证明这些机制的有限行为，不证明报告里的自由文本为真。

## 下一步应优先做什么

1. 将“题外未调查”与“不是修复”分开验收，避免错误的 not_repair 静默污染分母；进入点、角色、修复锚点的自洽性也应独立提示。
2. 对后置验证显式展示可查的后续时窗，区分“该 fixer 当次没编译”“全池后续有构建”“构建是否包含此补丁”。继续加口号式提示已经不足以稳定解决 C4。
3. 保留确定执行证据与文件状态复原的区别；没有复原版本不应否定原始脚本已记录的成功写入，同时不由此证明所有后续状态或设备行为。
4. 再用同题重复运行量稳定性，然后换未见项目。此 10 题已经用于优化，只能称开发回归集。

两原子不需要推倒重来；更迫切的是把错误结论、缺失证据和审计告警留在可复查的位置，而不是继续增加未经验证的归因边。

# 六小时迭代窗口与验收口径

用户追加要求：持续迭代约六小时，理想收尾是在评测集上证明节省20–30% token、归因正确性优于原始组、UI忠实。工作窗口记录为 2026-09-09 18:05 UTC 至 2026-09-10 00:05 UTC；这不是到点必须宣布达标的承诺。

## 固定指标，避免挑口径

- token 主指标：每次完整调查的 `input_total + output`，包含 guide、历史上下文、工具调用/返回、草稿检查和最终提交；缓存输入已包含在 input_total，不再加一次。另列 `input_uncached + output`、cache read 与端到端耗时。
- 同时报告每题、按调查任务归一化的平均变化与总量变化，不以最终回复字数或某一最好样本代替调查成本。金额不可得保持未知。开发/评委成本与产品调查成本分开，不假称整轮研发节省。
- 正确性同时看可查明事实召回、归因/责任/时间边界、错误断言和遗漏；不能全部写未知来刷准确率。严重错误包括虚构历史读写、错误作者、把后增义务当原有义务、把摘要/报告直接当底层验证。
- 机检只量来源、坐标、边、覆盖交代、最终提交一致性；不充当语义正确率。所有语义评分回原始转录核对，保存引用与不确定边界。
- UI要求完整真实步骤与实际来源、正确关系方向、候选/导航/模型主张分层、原因原文保真、无节点遮挡；需要浏览器与实际页面验证，不只模板字符串测试。
- 现有十题是开发集。另留5个未参与修改的问题做 question-level holdout；同一项目的不同题不冒充新项目泛化。参考答案在模型池外冻结，调优期间主线程不读holdout答案。

## 阶段

1. 完成既定 V6 八跑 document/reference 消融，不修改冻结 `4d5db4f`。
2. V6B 增加 Member 与 C4 的原始组，各2跑，共4跑：同冻结池、同 common task、同 GPT-5.5 medium、native transport、1800秒；沿用 V6 document case 的 `runs/raw/repN`，与工具目录分离。原始组只用只读 shell 检索转录，无 MCP、网页或额外参考。
3. 先完成 V6B 的 C4 raw rep1→rep2，再 Member raw rep1→rep2，与尚余 Member 工具队列共存时不超过2并发。原失败保留，不覆盖重试。
4. 在工作树修复静态/实页发现的问题：早期输入索引范围丢失、EOF空页、独立组件布局；给无法blame提供真实历史与原生补丁的导航诊断，但不把最近全文作者认作被修行作者。
5. 后续固定候选版本后，同题对照与完整开发集回归；参考草稿按哈希交付可减少重抄错误，但是否整体节省token和保住语义必须由实验决定。
6. 候选满足开发集门槛后再打开holdout评测；没达到则记录差距和失败样本，不修改答案或只挑成功的跑。

V6B原始组不承担工具组的账本坐标、coverage清单和UI结构化交付要求，因此 token 对比是两种产品调查流程的端到端负担，不是仅比较检索器效率。原始组也保留全部真实 shell调用/返回与报告，可以人工复核；不再宣称“原始组完全不可审计”。两种方式的共同语义题目与允许信息范围完全相同，额外可视化/结构化负担单列说明。

达标只可表述为固定评测集和重复次数下的观察；样本不足时不宣称总体统计优势。六小时结束前如仍不满足三项条件，给出已验证改进、未达标指标、失败归因及可继续的具体实验。

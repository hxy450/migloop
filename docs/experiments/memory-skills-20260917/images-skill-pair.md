## 观察指标

1. **调查范围**：是否仍是原单问题、多文件任务，未退回整文件盘点，未只交一个最容易目标。
2. **目标处置**：19目标分别有 graph 或 unresolved；报告两者数量，不能把“未决已登记”当“归因完成”。
3. **语义质量**：从真实稿件抽取归因，核实际输入、输出偏离、传播及最终保留修改。至少检查预分析中的 GuideInit、Mine、ManageRenew 和 padding 分支；检查共同机制是否被无证据外推到所有文件。预分析不是穷尽19文件金标，不伪造19项总准确率。
4. **可审计性**：可定位引用、真实读写/时序、脚本虚线及每个目标的实际检查状态。图通过不是原因正确。
5. **首稿→末稿**：是实质纠正责任/结论，还是仅改身份/时间/边；不可为了机械通过删除难点。原稿逐份保留。
6. **成本**：总输入、缓存、未缓存输入、输出、耗时和调查/封装工序。相同19目标任务相互比较，不与单会员页或单价格问题直接比较成本。

### 机械状态的精确口径

- 标准版：19图的 `mechanical_status=valid`；其中6图为 `complete + ready_for_review`，6图为 `needs_path + draft`，7图为 `complete + draft`。模型末答所说“13条完整”包括那7个没有问题起点的候选图，不是13个完成归因。

- ready 的含义是声明的身份、引用、时序与路径满足机械载入条件，**不认证 reason 正确、输入足够、问题传播或修改解释完备**。本轮没有逐个打开浏览器验收19个图。

## 下一步建议（本轮未实施）

1. **先解决语义停下标准的执行，不继续增加表单。** 找到写者不算完成；对于已标红的起点，需要在当次输出里定位本问题，并核其相关写前输入。找到明确边界时画入图；没找到就明确“生成归因未完成”。不能因有graph且机械ready便交差。
2. **统一任务拆分与制卡约定。** 这个旧job仍反复提示无真机复验、不可达候选；两份skill已经采用最终保留状态为参照，但模型仍花篇幅论证修复有效性甚至因缺截图降级。后续应统一产物契约，不靠在临时prompt反复覆盖；保留“未观测到运行症状”的事实，不把它设为追生成偏差的阻塞。
3. **对同一问题先区分机制分支，再决定展示多少图。** 19文件里有缺宽高、单轴缺比例、padding外框、参数/容器边界，不是一个统一根因。共享证据可以复用，但同类修复不能直接证明同一生成原因。现有每目标独立graph要求会产生重复交付负担，是否改成共享机制图加目标修复对账，需要另做设计/实验，不能从本次就断言它是唯一原因。
4. **把反馈做成可操作的小清单、全文可展开。** 优先展示哪句归因依赖哪条未核边、相应调用位置与目标问题，而不是让模型消费大份回执；保留完整检查产物供审阅。限制批量结果的坏交互、减少无效page，不能静默截断或丢材料。

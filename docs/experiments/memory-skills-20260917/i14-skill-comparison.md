# i14 调查方法迁入 skill：单问题验证

## 本次问题与边界

用户要求新建独立 skill，用 Luna 重跑，暂不回退代码。新建 `skills/migloop-build-cards-i14/`，保留已有四个 skill、inquiry 内核、UI 和旧实验产物；新 skill 复用原制卡格式和封装器。

这不是 i14 原环境重跑，也不是已完成的消融：此前同题为 Sol/high、没有 MCP；本轮为 Luna/high、新 skill、启用 MCP。成功只能证明此组合在当前代码上可完成该题，不能单独证明 skill 导致改善、代码没有退化，或广泛优于另一模型。

不回退的理由是后续代码包含取证和接口修正；没有证据表明整体回退比保留修复更好。代码因素尚未排除，尤其是旧 i14 自动从节点引用附边，而当前卡片显式声明路径，这一交付差别仍可能影响成本。

## 迁入了什么

来自 i14 冻结版 `interfaces.py` GUIDE 的方法，而不是该题答案：

1. 实际修复 calls/回执与不带关键词的生成、修复 outline 共同起步，防止只见原生 Edit 或被修复方措辞限制。
2. 先查相关片段演变，再查实际写者输入；区分早期骨架、后续业务接线和最终保留状态。
3. 对照实际交付要求、当次写出、后修标准；检查消息、历史 skill 和工具返回，不把原生 Read 表当全部输入。
4. 核正确输入与偏离输出后停止；声明、未命中和假设不升格为事实。
5. 批量查询、按需原文窗口、完整续读选定参数/回执；机械反馈要求重新审查依赖它的归因。

没有恢复旧版 findings/id/evidence 手填格式，也没有恢复“必须独立证明最终修复有效”的要求。新卡继续给 when、summary、recommendations 和最小输入—偏差—目标图；普通边证据仍由机器绑定。

## 预定审查项

分别报告，不用机械通过替代正确性分数，也不把单题换算为旧 27/28：

| 项目 | 判定依据 |
| --- | --- |
| 局部归因 | 对应实际交付输入和当次写出；不把后期具体行为倒灌给早期作者 |
| 停止边界 | 核相关正确输入的具体内容和交付，不只看路径或修复方声明 |
| 最终修复 | 描述本问题最终保留改动，有调用/回执或内容支持 |
| 单问题范围 | 不把已经另拆的修复中新生问题再次变成本卡独立根因 |
| 可加载图 | 关键正常输入节点、偏差节点和到目标的真实关系；准确记录普通边/force 状态 |
| 稿件修订 | 初稿、机械反馈、终稿均保留；错误归因若存在，核它是否真的被修正 |
| 成本 | 端到端时间、累计输入/缓存/未缓存/输出、MCP 与原始读取次数；不混淆累计输入与上下文大小 |

人工审查参考原始位置来自同目录 `review.md` 的独立核对，位于调查工作区之外，没有发给模型。

## 结果

### v1：指令读取受编码干扰，不能当作干净的 skill 效果测试

模型首个 PowerShell `Get-Content` 未指定 UTF-8，MCP 之外的新 SKILL.md 正文实际返回乱码，后续没有重新完整读取它；共享制卡约定和 job 后来使用 UTF-8 正常读取。因此不把该轮算成新 skill 已完整交付的成功实验。保留所有产物，不抹掉失败。

- 实际 Luna/high，543.46 秒。累计输入 4,690,901，缓存 4,476,416，未缓存 214,485；输出 23,042。
- 20 次 investigate、12 次 page、6 次 shell；壳层主要用于读 skill/job 和封装，不是沿用此前直接查 SQLite 的调查方式。
- 主归因正确区分了纯数字骨架与后来实际价格数据接线；但又把另拆的 helper 编译错误当作本卡独立 problem，缺少关键正常输入文件节点。
- 三次封装均 `needs_revision / needs_path`。初次将 agent 顺序错误地连成派发链；后来改成写者到目标的星形图。未解析脚本写边已经明确反馈 `force_eligible:true`，但模型没有使用允许的补证流程。
- 模型把后两次反馈用 `Select-String` 过滤，显示状态却没有显示 force 许可。它还覆盖了 `draft-1.yaml`；历史提交仍存在各 case 回执和原生运行转录中，不能说独立草稿文件已逐稿完整保留。
- 最后明确报告链路未完成，没有人工替它改稿后计为成功。

### v2：仅修正 skill 的读取编码后复测

新建 `luna-i14-price-v2`，同任务、同 skill 内容、同内核、同 Luna/high 与 MCP。唯一指令改动是在外部提示中把“使用”改为“按 UTF-8 读取并使用”；不包含 v1 的结论或错误提示。模型首次读取的实际工具返回已确认是完整正常中文。

此修改在模型启动前用最终 prompt 的 SHA-256 重新冻结，并记录到 manifest 的 `pre_run_prompt_override`。重现实验时需要保留这个操作性编码提示；不是第二轮继承第一轮会话。

实际 Luna/high，461.35 秒（7 分 41 秒）。累计输入 4,629,752，缓存 4,445,952，未缓存 183,800；输出 19,205。21 次 investigate（69 个查询项，包含一次误写的 op:page）、15 次 page（34 个续帧请求）、13 次 shell。主 skill 的首尾均在正常 UTF-8 工具返回中，运行后冻结验证通过。

**未通过。** 本轮没有达到正确归因与可加载图的交付标准：

- summary/origin 又归给最初 aconv-member，将后续读取的 Kotlin 当成生成之后才获得的标准。但该读取发生于 `2026-07-24T15:33:51.671Z`，早于任务的生成截止 `22:15:00.897Z`，属于生成期 aslice8-pay 的输入。
- 它虽然查询过这个后续生成 agent 的 returns，却没有展开其实际目标 Write `e-c56d4d99ddee` 或返回 `e-85c5349ca3fd`。实际收到正确源码与实际写出偏差没有在同一生成节点上对齐，不能因为总共查了许多条就算完成。
- 本次没有把正常修复者另标 problem，单问题范围较 v1 好；但“正确输入”节点的路径拼成了 Harmony 工程下的 Java 路径，实际应为 Android 工程路径。该节点还被错误解释为后修输入。
- 模型把约定的 `PYTHONPATH` 写成不被运行器读取的 `MIGLOOP_CARD_PYTHONPATH`，三次带 `--db` 的尝试均无法 import inquiry。最后自行省略 `--db`：卡片只有 `schema:passed`、`graph_check:not_run`，没有完成机械复核，不能载入时当作已验通过。
- 最终只一份 draft，未出现机械反馈推动归因修正的过程。没有向该会话补发正确作者、路径或时间提示。

#### 审查员后置验证，不能算作模型交付

在 `auditor/` 复制数据库，使用同一冻结 Python/代码、正确 `PYTHONPATH`，对**未改动的模型原稿**执行 pack，校验器立即正常运行并拒绝错误路径，返回 `nodes[1]` 和正确 Android 路径候选。证明这一轮“缺少可选依赖”的说法不准确，实际是调用环境没按约定接通；不证明语义校验足够。

该结果为 `auditor/checked-original.json`，与模型的 `workspace/case-1.json` 分开保存，没有覆写模型原始结果。

## 当前可确认的接口成本点

不能因暂不回退就认定代码已排除：

- i14 的正文帧按 9,000 字符；当前按整包转义 UTF-8 字节约束，并限制单帧。v1 的同一 18,402 字符源码窗口结果，单独完整发送按旧正文长度需 3 帧，当前 pack 需 4 帧。这只是同一 body 的分帧估算，不是完整耗时消融，也不主张撤销防截断保护。
- 当前 `cases.py pack` 把整份 validation receipt 打到终端；v1 首次实际 stdout 为 58,686 字符，后续模型自行过滤时漏了处理该问题所需的许可。说明可将完整回执保存为附件、默认输出精简但完整的错误/下一步；不是仅追加更多 prompt。
- runtime/数据库已在 job 中，却仍需模型手动设置 Python 导入路径并重复传 `--db`；v2 错调之后又能自行降成仅格式校验。这是应由入口消除的操作负担，而不是需要模型重新发明的调查步骤。下一次应让入口使用宿主配置、配置了数据库就不静默降级。
- 此次保持上述代码不动，避免在运行中更改条件。

# v3：去掉重复文本与非执行对账，不减少原文证据

v2 两个 Dice 重复调查在同源工具下，总输入分别为 2,492,193 和 880,848；仅凭这个差异不能说明账本逻辑提高了三倍效率。需看模型真正拿到了什么。

## 可复现的传输浪费

本机 MCP 1.29.0 的 FastMCP 会根据工具的 `-> str` 返回注解同时产生两份相同文本：`content[0].text` 和 `structuredContent.result`。逐个原始返回核对，Dice rep1 的 55/55 次、rep2 的 68/68 次均逐字重复。rep1 的首个宿主调用采用 `text(r)`，rep2 采用 `text(r?.structuredContent?.result ?? r)`。前者会把双份信封送回模型，后者只取一份。这与批次调度共同造成成本波动，不能简单以 MCP 调用次数解释成本。

原始记录：`_migloop-eval-20260909/v2/dice-entry/runs/tools/rep{1,2}/transcript.jsonl`。

| 运行 | MCP 调用 | 宿主批次 | MCP 正文字符 | 宿主返回字符 |
| --- | ---: | ---: | ---: | ---: |
| rep1 | 55 | 23 | 230,586 | 381,139 |
| rep2 | 68 | 15 | 203,353 | 199,417 |

宿主字符可能包括包装、选择或截断，不能与正文字符相加或当作 token。成本依旧取供应商原始 token 字段。

修正：九个文本查询显式 `structured_output=False`（支持该参数的 SDK），只保留标准 MCP 文本内容，不再制造第二套标量信封。原文、坐标、分页、查询参数和 readonly 注解不变；旧 SDK 不传未知参数。三个回归先红后绿，确认工具不再带重复 outputSchema、GUIDE 逐字保留一份、action 原文窗口和继续分页提示逐字不变。此为传输去重，不是摘要压缩；也不宣称总 token 一定减半，原来已自行抽取文本的客户端收益会小。

## 非执行事件不当作必须逐项解释的修复候选

仅对采集器明确创建的纯文本事件，且没有执行 ID、非读文件效应或不确定效应标记时，移出强制执行候选分母；它们继续存在于原文/提及索引中。外部修改自述仍可作为调查线索，排除不证明自述为假。

Dice 由 7 版本＋16 候选变为 7＋1，排除 8 think、3 inbox、3 say、1 inject；273 条提及未变。Splash 仍为 9＋15，图片 L233、遮罩 L103 均保留，679 条提及未变。没有依据命令摘要擅自认定 Bash 纯只读。

## 历史分母不重写

运行产物中的 harness 顶层 `repair_manifest` 保存当时的清单。载入时先核 ledger、文件、版本、事件身份与候选 hash，再沿用记录分母；不拿当前筛选策略把旧报告判为缺项或越界。策略变化在 UI 单列；记录非法时禁止认证完备，缺记录时明确只是当前规则下的对账。该元数据不能由模型 YAML 添加。

新策略标记 `execution-candidates/2`。范围登记完成仍不等于语义准确、设备验证或真实修复穷尽。

## 验证安排

MCP 传输去重与非执行候选精简是本批两个成本改动，不能将组合效果归给其中某一个。模型继续使用 GPT-5.6-sol / medium。GUIDE 的语义任务和共同 full-pool 提示保持不变；原始证据池不变。先在新冻结版本检查实际工具消费，再用未参与本轮调参的 MemberCenter 案例做两组调查；参照清单不提供给被测模型。仍按事实质量、原始用量及实际时间并列评价，不以引用数量判胜。

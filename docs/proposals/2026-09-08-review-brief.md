# migloop 返修链路账本:待评审的改动清单(2026-09-08)

给外部评审者的自足文档。先讲系统是什么、量到了什么,再列每条提议的改动(做什么 / 为什么 / 证据 / 代价 / 风险),
最后列出双方有分歧、需要裁定的点。评审者可以只看 §3 和 §4。

---

## 0. 背景

### 0.1 系统
- **对象**:一次 AI 代码迁移(Android → HarmonyOS)由几十到上百个 agent 在几十小时里完成,留下 Claude Code / Codex 的会话转录
  (主会话一份 jsonl + 每个子代理一份 jsonl,每条记录是一次工具调用的输入输出或一段正文)。
- **账本**:从转录建「两原子账本」——
  - **版本文件** `file(path, v)`:文件第 v 版,≤v 的全部写者(哪个 agent 在它自己的第几版写的、diff、来路),读了这一版的 agent,复原正文。
  - **版本 agent** `agent(id, v)`:一个 agent 做出第 v 个对外效应(写 / 删 / 派发子 agent / 发消息)之后的状态;派发它的人与派发词、收件箱、≤v 的全部读取(每条绑定读到的是文件第几版)、产出。
  - 其他工具:`action(id, n)` 展开一次调用的原始输入输出;`search(q, agent= | file= | until_ts=)`;`sessions` 列返修链;`blame` 逐行归属;`index` 目录。
  - 坐标:文件 `path@vN`,agent `id vK`,动作 `#n@L行`(动作号 + 转录行号,稳定指针)。
- **任务**:对修复阶段被改过的每个文件,调查模型(claude-opus-5)追一条链:每环「谁、凭什么、判定(传递 / 错 / 缺)」,指出故障进入点。
- **对照组**:同一模型不用账本,直接读原始转录(grep 文件名 + 读原文)。两组同题,第三个模型按环盲评。
- **展示**:返修链路页(两原子懒展开探索树),今天加了「调查树」:模型查过的节点自动长成向左的树,没查过的折成「+N 未查」桩,报告归因的链标红。

### 0.2 实验事实(已跑)
- 六根返修链(有生成方、修复方、缺陷单):工具组 vs 原始组,盲评从 1:5 修到 5:1(每根取最新一次)/ 3:3(全部重跑一次)。费用工具组低两到三成。
- pod730 三根「一个文件为什么被改了几十版」(没有修复阶段):原始组 3:0 赢,工具组费用持平、时间更快。
- 输掉的根按原因归类:**脚本 / 命令解不出效应**占一大半,且是唯一还在持续输的一类;其余是查询范围(已结构修)、模型判断、坐标可核性、跨会话指令边。
- 评委反复给原始组加分的一句话:「坐标带 UTC 秒级时间戳 + old/new 原文,可回查」。

## 1. 已定的原则(用户裁定,评审者可反驳但需说明理由)
1. **词法层全量**:凡命令文本里出现这个文件的全路径 / 相对路径 / 裸文件名,就算「沾边」,一条不少地摆出来;这层不做判断。
2. **可能的边只导航、不入账**:虚线边就是一行(谁、何时、命令片段、#n@L),不立版本、不进 diff / blame / 上游跳数。
3. **不追脚本黑盒**:循环变量、glob、目录级操作不做展开;「变没变」靠内容断点(后一次读到的内容与上一次已知不一致),
   「谁可能改的」靠断点窗口内有写能力的命令,只给数量和查法,不自动铺(费用)。
4. **判定按「节点 + 版本」落**,不按 id 连坐。
5. **树**:查过的都展示,以被修文件向左长,归因链标红,一个文件几条缺陷就几条链,按缺陷分组切换。

## 2. 提议的改动

每条:做什么 / 为什么 / 证据 / 代价 / 风险。

### A. 提及分档 + search 命中行带可能文件
- 做什么:「提到它的命令」按命令对这个路径能做什么分三档:改动类(cp、mv、sed -i、python、heredoc 落盘目标、重定向、rm、git checkout)
  与正文提到类逐条列;只读检查类(cat、grep、wc、ls、test、diff、git log)折成计数。每条带「这条命令里一共 N 个文件」。
  search 在 Bash 里命中、账本没记读写时,命中行带「可能碰到的文件」。
- 为什么:SplashPage 47 条未入账里大半是批量计数 / 存在性检查,铺出来是噪声;真正该看的(cp .bak 还原)排在后面。
- 代价:半天。风险:分类表是启发式的,但只影响折叠与否,不影响是否可达。

### B. 提及按版本窗口挂;断点带窗口候选数
- 做什么:版本 v 的窗口 = 上一版时刻到这一版时刻;命令按时刻落到窗口,挂在那一版下面。版本是「内容未知 / 实录外修改」时,
  窗口内改动类命令排最前,标为候选写者。「实录外修改」断点行给「窗口内有写能力的命令 N 条」+ `search(since_ts, until_ts, kind=write)` 的查法,不自动铺。
- 为什么:模型站在一个内容未知的版本前,现在得自己猜哪个 agent、哪段时间、哪条命令。
- 证据:0723 EntryAbility 四轮都输在 20 版 cp .bak 还原,那条命令现在已在「提到它的命令」里,但没挂到它产生的那一版旁。
- 代价:半天。风险:窗口枚举一旦自动铺,0723 一小时窗口约 60–70 条命令、约一万字,所以只给数量。

### C. agent() 槽里直接带「可能碰了 A.ets(#n)」
- 做什么:agent 视图每个版本槽里,解不出效应的命令不再只是「⚠ 未解析读写」,而是列出它提到的文件与当时版本。
- 为什么:现在要经 action 才看到。代价:小,依赖 A。
- 附带:`agent(id, v, until=#n)` 在那条命令处截断版本槽。一条账本没认出的写(比如 10:10 的 cp)落在版本 k 的槽里,
  槽一直延到 10:20 的下一个效应;从那条命令进来只想看它之前的输入,截断就不用看 10:10 之后的囊余。不改版本模型,只是视图截点。

### D. 树上画虚线
- 做什么:文件节点上游列,实线是确定写者,虚线是改动类可能写者(挂在版本窗口),只读提及折成灰桩「+N 只读提及」;虚线节点不展开子树,点它等于 action。
- 代价:半天,依赖 A、B。

### E. 报告引用与调查树落色改按 #n@L,不按 vN
- 为什么:版本号是计数,账本以后确认一次漏掉的写(重放 / 断言),同一 agent 和文件之后的版本号全部后挪;#n@L 不变。
- 代价:一两小时。这是 F 的最小替代。

### F. 坐标换时间(争议)
- 做什么:身份 = 时刻 + 动作号;`file(path, at=)`、`agent(id, at=)`、`search(since, until)`;版本号降为统计(改了几次 / 几个效应),
  不再出现在任何坐标里;树上标签 `slice11 @T+14:41`,写者分组节点显示时间段。
- 理由:(1) 稳,不随账本改版重排;(2) 跨 agent、跨文件直接比先后,评委四轮夸原始组的就是这一点;(3) 能懒(见 G)。
- 代价:渲染层、MCP 工具签名、GUIDE、probe、页面、三百个测试,一到两天;账本结构不动。
- 风险:模型抄时间戳比抄整数容易错(接受 T+ 相对与绝对 UTC,前缀唯一即认);同一毫秒并行调用要用动作号排序;跨机器时钟偏差。
- 用户的怀疑:是否关键?是不是只有这样才能连接工具调用带来的可能改动?——我的回答:不是唯一路径,可能改动已经经 action 连上;
  时间买的是稳、可比、可懒,不是连通性。

### G. 分层建账(争议,依赖 F)
- 做什么:先只收工具级 Read / Write / Edit / 派发(读 JSON 即可,约 4 s)就让页面和 file() 可用;shell 命令解析按 agent 后台跑或被查到才解析,
  解出的写按时刻插入时间线。
- 为什么:冷启动慢。用户的判断是「agent 只和文件、时间连线就能独立,不需要一开始就对应版本,应该一瞬间」;
  我的判断是慢在解析 shell 命令(11 s),不在对应版本(2 s);但用户的直觉指出了另一件事:版本号是全局计数,少解析一条 shell 写后面版本号全错,
  所以现在必须一次算完;换成时间坐标,时间线是开放的,可以分层、可以懒。
- 替代:parse_shell 按命令文本记忆化(11 s → 约 4 s)+ 每个 agent 解析结果落盘缓存(重启后 3 s)。用户表示不在意缓存,只在意冷启动。

### H. 版本带「解法」标签;对已知内容重放
- 做什么:每一版标来路:工具写 / heredoc 全文 / ast 读改写 / 重放 / 推断。对上一版内容已知、变换是纯函数的(sed、replace、re.sub 字面量模式),
  直接把变换作用在已知内容上算出结果立版本,标「重放」。
- 为什么:cp .bak 还原、sed 替换这类现在只是「提到」或「内容未知」,重放后是有内容的版本;模型看到「推断」知道该核。
- 代价:一天。风险:重放依赖上一版内容已知,链条一断就断。

### I. 词法层扩到工具输出
- 做什么:对 tool_result 正文也做路径 grep(git status 的 modified 列表、ls、构建报错点名文件、grep -rl 输出)。
- 证据:三个文件里账本已记的 shell 读中,126 条路径只出现在输出里(其中大部分分析器已按 stdout 反证记成读,但通用层没有)。
- 代价:半天。

### J. 调查树按缺陷分组
- 做什么:报告环的【A】【B】【C】标签进 probe,面板按缺陷切换,只留那条链红;默认全红带字母。
- 为什么:SplashPage 一次修复含三条独立缺陷(返回键 / 进度条 / 状态栏),三条链的红混成一片。

### K. 验证
- 完备性差集:对一个文件,拿文件名 grep 整份转录每一行,和词法层逐条对,差集为零才算「相对转录完备」。
- pod730 挑一处 glob 写,两组同题跑一次,坐实原始组在这一类上也盲(现有证据:原始组赢我们的每一处都是路径写在某处而我们没看见,没有一例是 glob)。
- 六根再跑一轮,看坐标改动后盲评的「可核性」一项是否翻转。

### L. 以后的会话在源头收效应
- post-Bash 做工作区快照(改了哪些文件、改成什么样、命令吐了什么),脚本内容根本不用解析。历史会话只能靠 A–I。

## 3. 请评审者裁定的分歧

1. **时间 vs 版本号作为坐标(F)**。用户:怀疑不关键,可能只是「文件需要统计版本」;我:稳 / 跨对象可比 / 能懒三条理由,但承认连通性不靠它。
   备选是只做 E。
2. **冷启动慢的根因(G)**。用户:因为文件版本要和 agent 一开始就对上;我:profile 显示对应只占 2 s,解析 shell 占 11 s;
   但「分层建账」确实要时间坐标才不重排。请评审者判断 profile 的解读是否成立,以及分层是否值得。
3. **虚线层会不会撑爆上下文(A/D)**。用户担心;我:分档后改动类通常十条以内,只读折计数;窗口枚举永不自动铺。
4. **放弃脚本黑盒(原则 3)是否正确**。双方同意「解析有天花板、越适配越 heuristic」;评审者可反驳,例如认为 glob 对目录已知文件集展开是确定的而非启发式。
5. **原始组能否找到 glob 写**。无证据,只有反证(它赢的每一处都是 grep 可命中的)。
6. **优先级**。我的顺序:E → A → B → C → D → (F/G 待裁)→ H → I → J → K。理由:先把连通性做通,再决定坐标;性能记忆化可随时插入。

## 4. 术语
- **效应**:让 agent 版本 +1 的动作(写 / 删 / 派发 / 发消息);读、命令、收件是「喂」下一版的输入。
- **实录外修改**:内容变了但没有记录在案的写(脚本动态目标 / 构建工具 / 人手),账本立断点。
- **内容未知**:知道有一次写,复原不出写后的内容(cp、拼接、re.sub 等)。
- **提及 / 沾边**:命令文本里出现这个路径,不判读写。
- **#n@L**:动作号 + 转录行号,账本对实录的稳定指针。
- **窗口**:相邻两个已知版本之间的时间区间。
